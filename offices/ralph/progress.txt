## 2026-08-11 - US-552 (Rex / Session 6)
Task: Pin Pi HDMI/KMS output to the panel-native 480x320 (kill downsampling)
Result: Deploy-side delivered and gated. **COMMIT OWED AGAIN** -- BL-032's stale
lock is still unclearable (~80 min, both remedies re-refused). Loop stopped with
HUMAN_INTERVENTION_REQUIRED rather than bank a third uncommitted story.

### What was implemented:
- **`deploy/set-display-mode.sh`** -- idempotent pin of the KMS output mode to
  the panel-native 480x320 via a `video=<connector>:480x320` token in
  /boot/firmware/cmdline.txt, wired into `deploy-pi.sh` as
  `step_set_display_mode` directly after `step_set_gpu_cma` (same class: an
  idempotent box-level boot-config re-assertion, after `sync_tree`, effective
  next boot).
- **It writes to cmdline.txt, which US-524 explicitly REFUSED to touch** (and
  pinned that refusal with a test). On a Pi 5 there is no alternative -- the
  legacy config.txt `hdmi_group`/`hdmi_mode` path is Pi 4-and-earlier firmware.
  So the risk is BOUNDED, not avoided, by four interlocks that are as much the
  deliverable as the pin: the connector is DISCOVERED from `/sys/class/drm`
  (a Pi 5 has two micro-HDMI ports); nothing is written unless EXACTLY ONE
  connector reads `connected`; the target must be a mode the PANEL ITSELF
  advertises; and the composed line is verified before install (one line,
  `root=` + every original token) and re-read after, restoring the pristine
  backup if it disagrees.
- **AC-1's "read the actual output mode" was IMPLEMENTED, not performed** -- the
  Pi is unreachable from this harness, so the deploy step reads it on the Pi
  every run (`/sys/class/graphics/fb0/virtual_size`, since kmsprint/xrandr are
  not installed there) and reports it, printing `unknown` rather than inventing
  a mode when unreadable.
- New gates `tests/deploy/test_set_display_mode.sh` (14 scenarios / 50
  assertions) + `tests/deploy/test_set_display_mode.py` (9 tests).

### Files changed:
- Created: `deploy/set-display-mode.sh` (the pin + the four interlocks)
- Modified: `deploy/deploy-pi.sh` (`step_set_display_mode` defined + called)
- Created: `tests/deploy/test_set_display_mode.sh` (scenario catalog)
- Created: `tests/deploy/test_set_display_mode.py` (catalog runner + wiring guards)

### Learnings for future iterations:
- **Pattern discovered (the one that unblocked the story)**: when an AC says
  "read X, and if X is wrong, fix it" and you CANNOT read X, do not guess and do
  not block -- **implement the read as part of the fix**. The script reads the
  mode on the Pi, decides there, and refuses loudly when the evidence is not
  what the story assumed. An unknown you cannot resolve becomes a machine-
  produced finding on the next deploy instead of a human step that never
  happens.
- **Pattern discovered**: when a new story must cross a line an earlier story
  deliberately drew (US-524: never touch cmdline.txt), do not quietly cross it
  and do not treat the old refusal as binding forever. Re-derive WHY it was
  drawn -- there it was "a safer mechanism exists" -- confirm that reason does
  not hold here, and then pay for the crossing with interlocks. Say so in the
  header of both files, or the next reader sees only an inconsistency.
- **Gotcha**: absence assertions pass VACUOUSLY on a missing script. The TDD red
  run reported "18 passed, 32 failed" -- those 18 were the `file NOT modified` /
  `no backup written` assertions, all trivially true because the script did not
  exist. Every refusal scenario therefore also asserts a POSITIVE (exit code +
  specific WARN content); a safety interlock proven only by "nothing happened"
  is proven by nothing.
- **Gotcha**: `deploy-pi.sh` runs under `set -e`, so a script's exit code IS
  deploy policy. Every deliberate no-op path must exit 0 or an unplugged bench
  panel halts the whole deploy. Pinned with a guard asserting the declared codes
  are exactly {0,1,2} -- `set-gpu-cma.sh`'s exit 3 is right for its case and
  would be wrong here.
- **Gotcha**: ground a constant against the DOC, not against a second copy of
  the literal in the test. The 480x320 default is asserted equal to the panel
  row parsed out of `docs/hardware-reference.md`, so swapping the panel goes red
  instead of silently pinning the old resolution at a new screen.
- **Gotcha**: a `pytest` run over several deploy files exceeded the Bash tool's
  120s default and was AUTO-BACKGROUNDED. It completed inside this iteration so
  nothing was lost, but pass `timeout` explicitly on any suite run -- TD-059 is
  about exactly this, and the auto-background is silent.
