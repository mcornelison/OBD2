### Learnings for future iterations:
- **Gotcha (the load-bearing one)**: an `rfcomm bind` is a KERNEL TABLE ENTRY.
  It outlives the ACL link AND it outlives the process. So (a) a dropped link
  leaves a device node that opens and is dead, and (b) a SIGKILLed predecessor
  leaves a binding the next process did not create -- which means any cleanup
  keyed on "did WE bind it?" (`_boundRfcomm`) skips, and `systemctl restart`
  does not clear the fault. When a resource lives in the kernel rather than in
  the process, ownership bookkeeping is the WRONG key; the configured identity
  is the right one.
- **Pattern discovered**: an IDEMPOTENT helper is a liability on a recovery
  path. `bindRfcomm`'s "already bound -> return the path" is correct for a
  first connect and is precisely the bug during recovery. When one function
  serves both first-acquisition and re-acquisition, give recovery its OWN
  entry point rather than adding a flag -- the flag will be defaulted wrong.
- **Gotcha (found by tracing, not by the AC)**: a teardown that destroys the
  very thing its own wait-loop probes for. `_reactToAdapterUnreachable`
  released the binding, then waited on `isRfcommReachable`, which requires the
  binding to exist -- unsatisfiable by construction. Check what the wait
  condition READS before choosing what the teardown DESTROYS.
- **Gotcha (test fidelity, the reason the existing US-221 flap test never
  caught any of this)**: it stubs the connection object, and the defect lives
  BELOW that -- inside `bindRfcomm`. Fake at the layer BELOW the bug (here the
  `subprocess` seam), never at the layer that contains it, or the test deletes
  the thing it is supposed to prove.
- **Pattern discovered**: bound a concurrency test through the SAME seam
  production uses to abort (here the orchestrator's `_shutdownEvent`). The
  first cut had no bound, so the RED run did not fail -- it HUNG the suite and
  left a daemon thread spinning. A regression must fail fast, not wedge CI.
- **Gotcha**: `waitForAdapter()` takes `maxIterations=None` in production
  deliberately (retry forever). Any test that drives it needs an explicit
  abort, and `sleepFn=lambda _: None` turns "forever" into a hot spin.

  generalizes**: my "stale speed" and "elapsed vs observed span" rules BOTH
  defend the same outcome (no false stop). The elapsed-time mutant SURVIVED
  because the test written for it was actually being saved by the freshness
  guard. When two guards defend one outcome, a test "for" either proves nothing
  until you disable the other -- widen/disable the sibling guard inside the
  test so only the rule under test can pass it.
- **Gotcha (the AC understated the defect in BOTH directions)**: the pitch was
  not raw accel-only -- US-478 low-passed the accel over 5 s. So a 1 s
  acceleration IS rejected and no bench test ever showed the bug; a 10 s
  on-ramp is 2 tau and propagates almost fully. A DELAYED defect is worse than
  an obvious one: it appears only under exactly the sustained input nobody
  reproduces at a desk. Read the filter constant, not just the formula.
- **Pattern -- derive a sign, never guess it.** Gyro-integrated pitch must
  agree with the accel tilt convention or the two halves of a complementary
  filter fight and the estimate is worse than either alone. Right-handed
  forward x left = up gives `omega x forward = -omega_left * up`, so nose-up is
  a NEGATIVE left-axis rate. Mutation-proved (flip -> 3 red). Also: an angular
  rate is a PSEUDOvector, so reusing a vector's mount-axis map is only valid
  for a proper rotation (det +1) -- true of every physical remount, false of a
  mirrored config typo. Documented rather than guarded.
- **Pattern -- check what is already on the bus before building a source.**
  `raw.imu.gyro` had been published since US-410 (same burst, same seq) with
  zero subscribers, and `raw.obd.SPEED` rides the same bus under the same
  `pi.bus.enabled` gate that builds this bridge. The whole ZUPT input was two
  subscription strings. The story looked M-sized and was mostly wiring.
- **Gotcha (the dangerous negative case, 2nd sprint sighting after US-518's
  route gate)**: it is the STALE reading, not the failed one. A BT drop while
  stopped at a light leaves "speed 0" as the last word; honouring it hard-snaps
  the attitude to the contaminated accel for the rest of the drive -- MORE
  confident than the drift it was fixing. Guard freshness BELOW the gate it
  feeds, and require evidence OBSERVED ACROSS a window rather than time ELAPSED
  since one reading (a slow poll otherwise manufactures stops).
- **Pattern -- feed a filter at the SENSOR rate, not the display rate.** The
  bridge writes at 10 Hz but bursts at 50 Hz; integrating only on written
  frames would silently discard four fifths of the rotation.
- **Gotcha -- a fallback is how a deleted defect comes back.** Leaving
  `gradePct` able to fall back to the gravity vector when the fusion is
  unseeded keeps every test green and quietly restores accel-only tilt.
  Mutation-proved. One published fact, one producer, and an honest
  `pitch_unseeded` null instead.
- **Process (3rd consecutive story to report it)**: a scoped in-loop selection
  cannot see the EXISTING guard for a contract it changes. I only avoided
  I-041's shape by hunting the states/imu exact-shape guard on purpose. The
  fix is mechanical -- run the existing tests for any contract you edit.

### Learnings for future iterations:
- **The load-bearing one -- PHANTOM CONFIG: a flag can be live on the box and
  absent from version control.** The RCA saw `--enable-gpu-rasterization` in the
  running cmdline, which reads as "the repo passes this." It does not, anywhere.
  Debian's `/usr/bin/chromium` is a WRAPPER that sources every file in
  `/etc/chromium.d/` into `$CHROMIUM_FLAGS`, then execs chromium with those
  flags FIRST and the caller's argv LAST. So `git grep` returns nothing while
  the process undeniably has the flag, and the fix is an ADDITION (override)
  rather than the deletion the story title assumed. When a defect points at a
  process's arguments, read `pgrep -a` on the box BEFORE grepping the repo --
  and when the two disagree, the gap is an OS-shipped file nobody owns.
- **Pattern -- turn an ORDERING argument into a NO-CONFLICT argument when you
  can.** The obvious fix (`--disable-gpu-rasterization`) requires believing a
  later `--disable-*` beats an earlier `--enable-*` inside Chromium's switch
  parsing -- true, but resting on internals I cannot verify from here. Choosing
  `--disable-gpu` instead let me verify something directly readable: I
  enumerated the entire injected flag set on the Pi and confirmed nothing in it
  is `--enable-gpu`. Unopposed beats last-wins, because unopposed is checkable.
  Prefer the fix whose correctness you can ground in evidence over the narrower
  one whose argument needs a source-code claim.
- **Gotcha (the mutation trap this story is built around): `--disable-gpu` is a
  SUBSTRING of `--disable-gpu-rasterization`.** A guard written as
  `assert "--disable-gpu" in unitText` passes on a unit carrying only the
  narrower flag -- it cannot tell the chosen fix from the rejected one.
  Tokenize the ExecStart (strip comments, join continuations, split) and assert
  LIST membership. The same helper is what makes a comment unable to satisfy the
  guard -- third sighting of that trap (US-501, US-513). Any guard over a
  flag/CLI string wants tokens, not text.
- **Pattern -- probe the fix live WITHOUT mutating the installed artifact.** I
  ran the composed flag set against the real dashboard URL on `DISPLAY=:0` in a
  throwaway `--user-data-dir` for 12s (alive, 0 AllocateRingBuffer, no GL init
  failure). Editing the installed unit to test it is how A-18 became a
  repo-unmanaged live fix that a reflash would silently lose. Probe BESIDE the
  production artifact, never through it -- then verify the CLEANUP too. My first
  cleanup attempt died with the ssh session and never ran; only re-checking
  showed the probe files still there.
- **Gotcha -- state the bound the evidence actually supports.** `--disable-gpu`
  does NOT remove the gpu-process; a software-GL one remains. The honest claim
  is "the v3d-on-64MiB-CMA exhaustion mechanism is gone," not "no GPU process
  runs." The weaker true claim matters operationally: the validation drill must
  read AllocateRingBuffer count + chromium CPU, not "is there a gpu-process."
- **Gotcha (ops)**: `make` is NOT on PATH on this box (nor `black`) -- `make lint`
  exits 127, which is easy to misread as a passing gate. Run `ruff check`
  directly and read the real exit code.

### Learnings for future iterations:
- **The load-bearing one -- for a SELF-HEALING component the dangerous default
  is "act", not "do nothing".** Every other story this sprint fights a display
  showing too little; a watchdog fails by doing too much. Two concrete traps fell
  out of that inversion. (a) `systemctl restart` on an INACTIVE unit *starts* it
  -- so the obvious one-liner would have had the watchdog usurping the splash
  `OnSuccess=` hand-off and lighting the dashboard on a DEGRADED boot, the exact
  honest-instrument rule dashboard.service.x11's A-1 note exists to protect.
  (b) An unreadable journal must be UNCERTAIN, never "wedged". Write the refusals
  as named reasons with one test each; the restart path is the short half.
- **A rate limit is only real if the action cannot outrun its own bookkeeping.**
  The ledger write happens BEFORE the restart, so an unwritable ledger CANCELS
  the restart. Written the other way round (restart, then record) every failed
  write silently uncaps the cooldown AND the budget -- and the tests stay green,
  because a fake ledger always writes. Order the effects, then assert the ORDER
  (`trace.index(write) < trace.index(restart)`), not just that both happened.
- **Gotcha (systemd; nearly cost the live states dir): a `RuntimeDirectory=` is
  DELETED when its unit exits.** The ledger wanted a tmpfs home and
  `/run/eclipse-obd` was the obvious one -- but a oneshot declaring
  `RuntimeDirectory=eclipse-obd` would have deleted that directory, *including
  the live `states/` every emitter writes*, every 30 seconds. The same
  directive's other edge: without `RuntimeDirectoryPreserve=yes` a oneshot's own
  dir is removed on every exit, so the ledger evaporates each fire, cooldown +
  budget always read empty, and the watchdog restarts the kiosk on EVERY tick --
  a flapper with a fully green unit suite. Both are guarded + mutation-proved.
  Before reusing another unit's runtime dir, check whether your unit's LIFETIME
  is shorter than the dir's contents need to live.
- **Pattern -- refuse the ungroundable half of an AC, and say so in three
  places.** AC1 offered marker-rate OR "CPU-pegged chromium with no
  state-file-driven repaint". Repaint is not observable from outside the browser
  (`states_http_server` silences per-request logging at :183, so there is no
  access log to read a heartbeat from), and the CPU half has no post-US-522
  baseline -- Atlas's 39/31/24%-vs-18/9/8% figures predate `--disable-gpu`, and
  software rendering raises healthy CPU by an unmeasured amount. A threshold
  there would be a fabricated number (Rule 2). Building the observable half and
  stating the bound beats both inventing the number and blocking the story.
- **Gotcha -- a watchdog can LAUNDER the bug it recovers from.** Infinite
  restarts would make a live freeze class look like a healthy display. The hourly
  budget converts recurrence into a persistent FAILED unit (exit 2 against
  `SuccessExitStatus=0`), and the restart log line names US-522 so a reader knows
  a restart means that fix did NOT hold. When adding recovery for a defect a
  sibling story just "fixed", make the recovery's own firing legible as evidence
  AGAINST the fix.
- **Ops gotcha**: a broad `pytest tests/deploy tests/lint ...` on this SMB share
  exceeds the 120s Bash default and is auto-BACKGROUNDED -- TD-059 by accident,
  not by choice. Pass an explicit long timeout so the gate stays in the
  foreground.
